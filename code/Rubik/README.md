# God's number in Rocq

Machine-checked proofs of three results about the Rubik's cube. The written
account is **`../../doc/rubik20-note.pdf`** (source `rubik20-note.typ`): it
explains the method and the measurements, and is the place to start.

**1. The superflip cannot be solved in 19 face turns**, so God's number is at
least 20.

```coq
Theorem superflip_p1far_real : superflip \notin ball Sset p1depth.  (* Farp1inst.v *)
Theorem rubik_diam_gt_19_real : ~~ diam_le Sset 19.                 (* Diam20.v    *)
```

**2. Reid's position cannot be solved in 25 quarter turns**, so in quarter
turns God's number is at least 26. The position is the superflip composed
with the four-spot pattern (Reid, 1998).

```coq
Theorem qdiam25 : ~ diam_le Sq 25.                                  (* HAll.v      *)
```

**3. Every position of the superflip's coset is within 20 face turns.** The
coset is taken for the subgroup *H* generated by the 10 moves that keep the
top and bottom faces in place. It has 19 508 428 800 positions. The published
upper bound runs one such check for each of 2 217 093 120 cosets; this is one
of them. It is proved twice, over the unfolded map and over the map folded by
the 16 symmetries.

```coq
Corollary superflip_row_fold h :
  h \in H -> superflip * h \in ball Sset 20.      (* RowFoldCubDone.v, folded map   *)
Corollary superflip_row_cub h :
  h \in H -> superflip * h \in ball Sset 20.      (* RowCubDone.v,     unfolded map *)
```

`Diam20.v` also states `rubik_diameter`, which takes the upper half (20 moves
always suffice) as a hypothesis. That half is not proved here: one coset is
not the 2 217 093 120.

Each theorem file ends with `Print Assumptions`. It names only the primitives
of Rocq's machine integers and arrays.

## The measurements

All on the same machine, a dual-socket Intel Xeon E5-2667 at 2.9 GHz, with 24
threads and 62 GB of memory.

**1. The 20 face turns**, at radius 19.

| | |
|---|---|
| building the tables, from clean | 1 h 02 of wall clock, 2 h 35 of processor time |
| the search | 5 h 48 of wall clock, 89 h 27 of processor time |
| pieces, workers | 30 pieces, 18 workers of 3.6 GB each |
| positions visited | 137 607 893 106 |

**2. The 26 quarter turns.**

| | wall clock | processor time |
|---|---|---|
| building the table, in OCaml | 9 min 50 | 1 h 43 |
| the same table as 59 Rocq files | 3 h 13 | 6 h 50 |
| checking the distance table, 12 jobs | 2 h 51 | 31 h 42 |
| the 6 searches, 72 pieces, 12 workers | 4 h 00 | 45 h 54 |
| **the whole chain in Rocq** | **10 h 32** | **87 h 29** |

**3. The superflip's coset**, 20 levels. The run is the `Qed` of the Bool
file, on one core.

| the run | time | the map |
|---|---|---|
| over the folded map, `RowFoldCubBool.v` | 50 min | 248 MB |
| over the unfolded map, `RowCubBool.v` | 2 h 32 | 3.25 GB |

The OCaml version of the same run (`ocaml/rubik_row_fold`) takes 30 min
unfolded and 25 min folded. In Rocq the fold gains a factor of 3, in OCaml
only 1.2: in Rocq, memory is the limiting factor.

## Running it

Everything runs on a large machine; the table builds alone need 12 GB a
worker. Raise the stack limit first: `ulimit -s unlimited`. Run the three in
this order: each one generates tables the next one needs, and `_CoqProject`
lists them.

### 1. The 20 face turns

```sh
make p1jobs             # the -j the run would use, and why
DEPTH=16 make test      # a short run of the whole chain, minutes
DEPTH=19 make test      # the real one, a night; it ends with Diam20.v
```

`make test` emits and checks the folded phase 1 table if it is missing
(`mkfold.sh`), writes the 30 search pieces at the chosen depth
(`mkrunp1.sh`), builds `Farp1inst.vo` and, at depth 19, `Diam20.v`. Files
already built are kept, so an interrupted run continues where it stopped.

**The job count is a memory question.** Each piece loads the phase 1 table,
so more pieces than the RAM holds do not run slowly: they stop.
`Makefile.local` computes the job count from the RAM present; `P1RUN_GB`
overrides the cost it assumes per job.

### 2. The 26 quarter turns

```sh
make hjobs              # the -j the run would use, and why
make htest              # the table, the 6 searches, the sweeps, and qdiam25
```

`make htest` needs `ocaml/h_fold14.tbl` and says how to build it if it is
missing (`cd ocaml && make hbuild JOBS=18 && make hfold`). It refuses to start
while `/dev/shm` still holds a table, since that is RAM the run needs.

### 3. The superflip's coset

```sh
./mkp1.sh                         # the unfolded phase 1 table, P1Table.v (3 workers)
make -j18 RowFoldCubDone.vo       # the folded map: the run is RowFoldCubBool.v
make -j18 RowCubDone.vo           # the unfolded map: the run is RowCubBool.v
```

Each run is one `Qed`, in a file of its own (`RowFoldCubBool.v`,
`RowCubBool.v`). The proof that uses it is in another file
(`RowFoldCubProof.v`, `RowCubProof.v`), which runs nothing. **Do not edit the
tree during a run**: the `.vo` records the digest of every file it depends
on, so a `git pull` in the middle throws the run away.

## What is where

### The cube, as mathematics

| | |
|---|---|
| `Cyc.v` | cyclic permutations, built from the list of points they move |
| `Rubik333.v` | facelets, the six faces, the eighteen moves, the cube group |
| `Sym.v`, `Sym16.v` | the 48 symmetries of the cube; the 16 the fold uses |
| `Ball.v` | balls of radius *d*, and what "the diameter is at most *d*" means |
| `Diameter.v` | the superflip, its 20-move word, and what an upper bound would need |

### The search, in the abstract

| | |
|---|---|
| `Search.v` | the search and its contract: a false answer is a proof |
| `Coord.v` | any summary plus any checked table gives a legal estimate |
| `Root.v` | the first move, up to symmetry: *U* or *U²* |
| `Searchr.v`, `Redun.v` | the rules that forbid redundant move sequences |

A run file loads no proof and a proof file runs nothing. That is why the two
are always separate files, and why a `.vo` banked by a long run must not
have anything under it edited.

### The certificates

The files that run the checks, each ending in its own `Qed`: `FsmChk.v`,
`FsrChk.v`, `SlrChk.v`, `P1TsChk.v` for the move and distance tables and the
second summary table, `Farp1chk.v` for the shape of the main table, and the
`Fold` group with its slices `FoldOrbit_00.v` … `FoldOrbit_26.v` for the folded
table.

The files holding the actual table data are deliberately kept out of
`_CoqProject`, since they do not exist until the generators have run and
`coqdep` would refuse the whole project.

## Outside Rocq

`ocaml/` holds the reference implementations, with its own `README.md` and
`row-programs.md`. **They are the specification**: the Rocq searches reproduce
their node counts exactly, which is how a discrepancy gets caught early.

| | |
|---|---|
| `rubik_par.ml`, `rubik_lb.ml` | the face-turn search |
| `rubik_qtm.ml`, `rubik_reid.ml`, `rubik_h.ml` | the quarter-turn search, Reid's table and its fold |
| `rubik_row_nofold.ml`, `rubik_row_fold.ml` | one coset, with the unfolded and the folded phase 1 table; `ROWFOLD=1` folds the map too |
| `rubik_row_rocq.ml` | the Rocq run translated to OCaml line for line, to see where the time goes |

The face-turn program's prefix filter was unsound until 2026-08-13 — it dropped the three
bottom-face second moves, searching 24 prefixes where 30 are needed, and so
skipped 29.6% of the tree while running to completion and reporting the answer
we expected. Writing the Rocq proof of that same cut is what found it.

`bench/` holds `p1gen.ml`, which generates the tables, and the experiments that
settled the design questions, each with its measurements.
